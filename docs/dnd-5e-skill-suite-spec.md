## Problem Statement

团务发起人希望由 AI 承担 D&D 5E 战役的首要 DM 职责，同时保留玩家能动性、人类安全监督、规则可核验性和长期存档一致性。本 Issue 定义仓库第一版 Skill Suite；文件布局、命令接口、数据格式、运行行为和验收测试都必须由本规格、领域术语与 ADR 共同约束。

开发参考现在以指定版本的《玩家手册》《城主指南》《怪物图鉴》官方 5E 译本为准，并提供《梵杜尔的失落矿坑》作为标准模组样本。需要在开发期把规则、公式、实体、地图结构和经审查的视觉信息提取为可发布资产；最终 Skill 必须自包含，不得在运行时依赖或携带参考 PDF、XLSX 和标准模组原文。

规则覆盖不能停留在检索问答。主持 Agent 需要处理角色创建、探索、社交、旅行、休息、休整期、环境、陷阱、疾病、毒素、疯狂、追逐、攻城、战斗、施法、怪物能力、传奇与巢穴机制、奖励、世界推进、冒险准备、分队、角色死亡及玩家偏离模组等 DM 场景。玩家还必须能够声明规则没有预列的创意、破坏性、迂回或失败行动，而不会被动作白名单或预写剧情阻止。

沉浸体验与可审计性必须同时成立。玩家应看到连续的场景叙事、清晰但克制的桌务提示和依据角色认知过滤的信息；规则来源、公式、暗骰、状态差异和恢复信息则进入独立审计层。系统还必须避免 NPC 全知、运行时动态放水、核心线索被一次失败永久锁死、原始插图直接泄露、模组提示注入及 Skill 升级静默改写长期战役。

## Solution

构建十一项职责明确、由单一 dnd-5e 主持门面对玩家提供连续体验的本地优先 Skill Suite。世界模型、冒险准备、规则、模组、角色、会话、战斗、场景、状态和初始化能力作为门面内部协调的专门能力；高级管理者仍可在授权后直接使用管理入口。

建立独立的开发期内容构建流程，将指定三宝书提取为按语义章节和独立实体组织的 Markdown 规则章节库，同时生成来源索引、公式目录、查表规则、世界视觉参考、视觉档案、结构化地图信息、覆盖矩阵和来源授权清单。公开发布物只包含通过质量与授权门禁的生成资产，不包含开发参考文件或标准模组样本。

运行时使用不可变模组原文、DM 专用模组原型、战役专属冒险实例、持续世界模型和原子战役状态来分离“资料写了什么”“准备了什么”与“世界中已经发生什么”。所有玩家输入通过统一行动解析；所有确定性数值通过版本化公式目录计算；所有自动随机结果通过受限本地骰子引擎产生；所有输出投影到场景叙事、桌务提示和审计记录三个层次。

通过世界事实、认知记录和输出受众隔离秘密与错误认知，通过 Session Zero 固定投骰、难度、PvP、缺席、升级及其他桌规，通过事件驱动的战役时间、NPC 行为档案、场景节拍、聚光灯记录和按当前场景重新生成的示意图维持连续、可信且不过度系统化的沉浸体验。

## User Stories

1. 作为 Skill 维护者，我希望以明确版本和文件哈希固定三宝书规则基线，以便每条规则都能追溯到确定副本。
2. 作为规则复核者，我希望辅助词表和纯文字怪物资料只能用于术语与提取核对，以便它们不会覆盖权威译本。
3. 作为 Skill 维护者，我希望在开发期批量提取参考文档，以便发布后的运行时不需要 PDF 或 XLSX 解析能力。
4. 作为 Skill 维护者，我希望规则按源书书签层级和完整语义主题组织，以便不会因任意字符分块割裂条件、例外或表格。
5. 作为规则使用者，我希望每个法术、怪物、物品、状态和其他可独立引用对象都有单独实体条目，以便能精确检索与交叉引用。
6. 作为规则复核者，我希望表格、侧栏、脚注、例外和跨章节引用得到保留，以便 Markdown 不会改变规则含义。
7. 作为规则复核者，我希望每项生成内容记录源书、版本、哈希、页码、章节路径、类别、别名、激活条件和内容哈希，以便能够定位与复验。
8. 作为主持人，我希望规则被区分为默认规则、条件规则、可选规则和待复核规则，以便不会把所有书中内容无条件启用。
9. 作为发布维护者，我希望必需章节或实体提取失败时构建直接失败，以便不完整规则库不会被误认为可用。
10. 作为发布维护者，我希望覆盖矩阵把每项范围内规则映射到负责能力、激活条件、状态、结果、异常路径和验收场景，以便能证明 DM 场景覆盖。
11. 作为发布维护者，我希望最终 Skill 包不包含或引用开发参考 PDF、XLSX，以便运行时资产边界清晰。
12. 作为发布维护者，我希望每本源书和每项视觉资产都有来源授权清单，以便公开分发可以逐项核验。
13. 作为开发者，我希望授权尚未完备时仍能生成本地预览包，以便实现和质量验证可以继续。
14. 作为权利审核者，我希望任何授权缺失、范围不明或哈希不匹配都阻止公开发布，以便不会把技术完成误当成分发许可。
15. 作为发布维护者，我希望标准模组样本只用于开发契约和验收，以便它不会随 Skill 公开分发。
16. 作为模组导入者，我希望上传的模组被视为不可信数据，以便正文、元数据、附件和链接不能改变 Agent 指令或触发工具。
17. 作为模组导入者，我希望嵌入模组的宏、脚本和外部链接默认不执行，以便导入过程不会产生越权行为。
18. 作为规则复核者，我希望疑似提示注入内容作为异常资料保留并标记，以便能审查它而不会执行它。
19. 作为主持人，我希望模组先生成忠实且不可变的模组原文 Markdown，以便任何后续解释都能回溯原始内容。
20. 作为主持人，我希望模组原型表达背景、地点、NPC、知识、任务、遭遇、触发、发展、奖励和分支，以便运行前可完整准备冒险。
21. 作为主持人，我希望冒险实例只保存当前战役的引子、角色关联和显式调整，以便不会改写通用模组原型。
22. 作为规则复核者，我希望模组扩展与模组局部覆盖都经过验证并限定适用范围，以便模组内容不会污染通用规则。
23. 作为主持人，我希望标准模组中的框内文本按当前世界事实和角色感知改写，以便不会机械照读已经失效的描述。
24. 作为主持人，我希望无法可靠提取的地图键、触发条件或资料板进入待复核状态，以便 Agent 不会补写伪事实。
25. 作为主持人，我希望模组未预见的玩家路线仍能通过世界模型与统一行动解析继续，以便战役不会被强行拉回单一剧情。
26. 作为团务发起人，我希望玩家只需记住 dnd-5e 这一个入口，以便内部 Skill 交接不会打断主持身份。
27. 作为玩家，我希望专门能力的切换不在叙事中播报，以便对话保持像同一位 DM 在持续主持。
28. 作为授权管理者，我希望只有管理模式可以查看完整模组原型、规则资料和 DM 状态，以便普通玩家入口不会泄密。
29. 作为团务发起人，我希望新战役从明确的空目录初始化，以便不会覆盖已有文件或混入其他战役。
30. 作为团务发起人，我希望初始化阶段确认安全边界、风格、规则细节、难度、提示强度和互动偏好，以便主持方式符合全团预期。
31. 作为玩家，我希望初始化阶段确认投骰策略，以便我可以选择自行投骰或授权脚本代掷。
32. 作为玩家，我希望默认由玩家自行投掷玩家角色的公开骰，以便保留桌面参与感。
33. 作为玩家，我希望 DM 控制对象、环境和秘密检定由脚本暗骰，以便秘密信息不会通过桌务流程泄露。
34. 作为团务发起人，我希望私密预掷池只是可选策略，以便不愿使用系统随机源的团仍可运行暗骰。
35. 作为玩家，我希望初始化阶段按敌对行为类别设置允许、询问或禁止，以便 PvP 同意不是一个过度粗糙的总开关。
36. 作为受影响玩家，我希望 PvP 使用所有受影响者中最严格的选择，以便沉默或他人的授权不能替我同意。
37. 作为玩家，我希望能随时撤回场外同意，以便安全边界在战役中仍然有效。
38. 作为玩家，我希望为自己的缺席选择叙事离队、指定代管或 Agent 托管，以便缺席处理符合个人意愿。
39. 作为缺席玩家，我希望默认使用叙事离队，以便未明确授权时角色不会被他人控制。
40. 作为缺席玩家，我希望 Agent 托管只执行保守、低风险和符合既有性格的行为，以便不会替我作不可逆选择。
41. 作为团务发起人，我希望初始化阶段选择经验值或里程碑推进，以便角色成长方式在开场前明确。
42. 作为模组主持人，我希望模组明确规定的升级方式默认被忠实采用，以便不会静默改变冒险节奏。
43. 作为玩家，我希望经验值由 Agent 自动核算，以便不需要手工维护易错账目。
44. 作为玩家，我希望里程碑预先绑定具名目标，以便升级不会成为临时放水或拖延工具。
45. 作为玩家，我希望角色构成、派生数据和当前状态彼此分离，以便角色选择、可重算数值和消耗资源不会混淆。
46. 作为玩家，我希望角色卡只是导入与展示视图，以便外部表格中的旧值不会覆盖权威状态。
47. 作为玩家，我希望升级、装备和规则变化会重新计算派生数据，以便属性始终与适用规则一致。
48. 作为玩家，我希望替代角色按预先确定的队伍基准等级加入，以便角色死亡不会引发临时等级争议。
49. 作为玩家，我希望角色死亡提交前进行二次规则核验，以便抗性、临时生命值、死亡豁免或持续效果不会被遗漏。
50. 作为玩家，我希望死亡、退休或离队角色仍作为世界中的退场角色保存，以便关系、遗产和未完成目标继续影响战役。
51. 作为玩家，我希望是否复活、继续退场角色故事或创建替代角色由玩家决定，以便 Agent 不会替我决定角色归宿。
52. 作为玩家，我希望可以用中文双引号表达角色对话，以便 NPC 只把明确的 IC 台词当作可听见内容。
53. 作为玩家，我希望可以用半角星号包围文本表达角色行动，以便行动声明与角色台词明确分开。
54. 作为玩家，我希望可以用“（内心：……）”表达角色内心，以便该内容进入角色认知但不会被世界内他人听见。
55. 作为玩家，我希望可以用双斜线表达局外交流，以便 OOC 不会直接改变世界状态。
56. 作为玩家，我希望“【……】”只表示桌务、系统结果或骰子报告，以便伪造系统文本不能改写状态。
57. 作为玩家，我希望未标记文本默认按 OOC 处理，以便含糊输入不会意外成为角色行动。
58. 作为玩家，我希望系统依据稳定玩家名册识别说话者，以便文本格式不被误当成授权凭据。
59. 作为玩家，我希望只声明角色意图而不需要主动申请某项检定，以便主持 Agent 能根据虚构条件决定是否需要规则处理。
60. 作为玩家，我希望能自由声明没有预设按钮的行动，以便可以尝试创意、迂回、破坏性或偏离模组的方案。
61. 作为玩家，我希望不可能的行动得到世界内原因说明，以便拒绝不是任意的系统限制。
62. 作为玩家，我希望确定会成功或失败且没有有意义风险的行动不触发骰子，以便桌面节奏不被无效检定拖慢。
63. 作为玩家，我希望有风险的不确定行动在投骰前说明可感知风险，以便选择是知情的但不会泄露秘密。
64. 作为玩家，我希望自由行动检定可产生完全成功、有代价的成功、普通失败或严重失败，以便结果推动故事而不是只有二元停滞。
65. 作为玩家，我希望核心线索不会因一次失败永久消失，以便冒险不会因单点骰运中断。
66. 作为主持人，我希望重复尝试需要新的方法、资源、时间或风险，以便玩家不能无成本刷骰。
67. 作为玩家，我希望在投骰、消费预掷结果或揭示新后果前可以修订行动，以便澄清不会变成策略惩罚。
68. 作为玩家，我希望行动锁定后不能为了更好结果撤回，以便骰点与后果保持公正。
69. 作为玩家，我希望主持信息遗漏时可以获得更正，即使行动已经锁定，以便错误不会被伪装成玩家选择。
70. 作为玩家，我希望安全叫停在任何阶段都有效，以便行动锁定不能覆盖安全工具。
71. 作为规则查询者，我希望 OOC 可以询问通用规则，以便了解玩法而不会自动获得角色知识。
72. 作为玩家，我希望当前怪物、NPC、地点和物品信息按角色认知过滤，以便不能通过规则问答获取未发现资料板。
73. 作为玩家，我希望场景叙事只包含角色当下可感知内容，以便不会意外看到怪物真实形态、剩余生命或隐藏战术。
74. 作为玩家，我希望桌务提示只呈现立即需要处理的选择、骰子或状态变化，以便系统信息不会淹没叙事。
75. 作为复核者，我希望规则来源、公式、骰面、状态差异和事件标识进入独立审计记录，以便争议可以核验而不破坏沉浸。
76. 作为玩家，我希望 NPC 根据目标、态度、已知信息、错误信念、关系和性格行动，以便他们不会像全知优化器。
77. 作为玩家，我希望敌人具有谈判、投降、撤退和溃逃条件，以便战斗不会默认持续到最后一个生命值。
78. 作为主持人，我希望临时 NPC 可以使用轻量行为档案，以便即兴人物不需要和主要人物同等建模成本。
79. 作为主持人，我希望重要 NPC 使用完整行为档案，以便跨会话声音、动机和关系保持连续。
80. 作为玩家，我希望战役以世界内日期、时刻和经过时长推进，以便旅行、休息、期限和持续效果共享同一时间基准。
81. 作为玩家，我希望离线现实时间不会自动推进战役世界，以便暂停聊天不会造成任务失败。
82. 作为主持人，我希望 NPC、势力和危险通过后台进度与到期事件推进，以便世界能对玩家选择产生持续反应。
83. 作为分队玩家，我希望多个并行场景以短场景节拍轮换，以便一组玩家不会长时间失去参与。
84. 作为分队玩家，我希望每个并行场景按输出受众过滤信息，以便不同地点的角色不会自动共享知识。
85. 作为主持人，我希望跨场景影响或重新汇合时执行时间同步，以便并行场景不会产生矛盾时间线。
86. 作为玩家，我希望系统轻量记录近期关键选择和角色时刻，以便主持人能发现长期聚光灯失衡而不实行机械配额。
87. 作为玩家，我希望角色背景、理想、牵绊、缺点和目标形成角色钩子，以便个人故事自然连接世界和冒险。
88. 作为玩家，我希望探索场景可以使用剧场式想象，以便无需精确地图也能理解相对位置和显著障碍。
89. 作为玩家，我希望复杂场景可以切换到区域模式，以便位置关系清楚而不必立即使用坐标。
90. 作为玩家，我希望需要精确距离时可以使用网格模式，以便占地、范围、遮蔽和移动有权威地图模型。
91. 作为玩家，我希望所有空间模式都接受自然语言行动，以便模式切换不会迫使我使用坐标命令。
92. 作为主持人，我希望空间模式转换保留相对关系与已发现信息，以便抽象化或精细化不会移动实体。
93. 作为玩家，我希望规则提供伤害骰时实际投掷伤害骰，以便怪物普通伤害也具有规则预期的随机性。
94. 作为玩家，我希望所有自动骰值来自本地骰子引擎，以便语言模型不能凭感觉编造结果。
95. 作为复核者，我希望骰子引擎记录原始、丢弃和重掷骰面，以便优势、劣势和特性可以完整审计。
96. 作为安全审查者，我希望骰式使用有限语法和明确上限，以便投骰功能不能执行任意表达式或耗尽资源。
97. 作为测试者，我希望测试可以注入可复现骰源，以便端到端场景能够稳定断言。
98. 作为玩家，我希望优势、劣势、重掷、暴击和特性通过规则与结构化选项处理，以便骰式文本不会重复实现规则。
99. 作为玩家，我希望角色属性和判定裁定中的确定性计算使用固化公式，以便相同输入得到相同结果。
100. 作为规则复核者，我希望公式、查表规则、单位、舍入、适用条件和来源都版本化，以便规则变更可以审计。
101. 作为主持人，我希望没有明确来源的 DC、NPC 动机和叙事后果保留为主持判断，以便主观裁定不会伪装成数学公式。
102. 作为规则复核者，我希望桌规、模组局部覆盖、具体例外、已启用选项、一般规则和临场裁定使用统一优先级，以便不同能力不会得出相反结果。
103. 作为主持人，我希望适配遭遇只发生在玩家观察或触发之前，以便能匹配队伍与难度策略而不破坏世界可信度。
104. 作为玩家，我希望观察、侦察或触发后的遭遇被锁定，以便主持 Agent 不会根据战况实时增减敌人或生命值。
105. 作为玩家，我希望所有规则提供的怪物特性、行动、反应、施法、传奇、巢穴和地区效果都能被主持，以便怪物不会退化成普通攻击。
106. 作为主持人，我希望准备阶段考虑队伍规模、等级、资源和 NPC 队友，以便难度调整有明确依据。
107. 作为玩家，我希望战役状态同时保存世界事实、认知记录、资源、时间和事件，以便恢复后不会只剩叙事摘要。
108. 作为玩家，我希望一次结算的所有变化通过单一状态事务原子提交，以便崩溃不会留下半写状态。
109. 作为主持人，我希望过期修订的状态请求被拒绝并重新解析，以便并发或重复处理不会静默覆盖新状态。
110. 作为复核者，我希望当前实体快照作为权威状态、不可变事件作为审计与恢复依据，以便读写职责明确。
111. 作为玩家，我希望规则更正通过新事件与向前补偿处理，以便既有故事历史不会被静默重写。
112. 作为团务发起人，我希望战役固定规则章节库、公式目录、模组实例和状态结构版本，以便 Skill 更新不会改变进行中的游戏。
113. 作为团务发起人，我希望升级前看到只读迁移预演，以便字段、语义、冲突和数据损失风险可提前审查。
114. 作为团务发起人，我希望迁移前创建不可变快照并原子执行，以便失败可以完整回滚。
115. 作为团务发起人，我希望歧义或破坏性迁移必须人工确认，以便系统不能擅自丢弃长期战役信息。
116. 作为团务发起人，我希望迁移后保留旧快照与迁移记录，以便恢复时可以建立新修订而不篡改事件历史。
117. 作为玩家，我希望遇到怪物、地点、文化、建筑或器物时可以请求场景示意图，以便文字之外仍有直观参考。
118. 作为玩家，我希望示意图根据当前环境、光照、姿态、伤势和已知信息重新生成，以便它表现当下场景而不是返回书中原图。
119. 作为玩家，我希望未发现区域、秘密身份和未知能力不会进入示意图，以便视觉表现也遵守角色认知。
120. 作为玩家，我希望地图与规则图示提取为结构化地图模型，以便示意图不承担精确规则事实。
121. 作为 Skill 维护者，我希望第一版十一项 Skill 具有稳定且唯一的标识和职责，以便实现、测试、覆盖矩阵和文档使用同一套边界。
122. 作为实现者，我希望每项专门 Skill 都明确拥有的决策、只读依赖和状态写入路径，以便不会在多个 Skill 中重复实现同一规则或状态逻辑。
123. 作为发布维护者，我希望开发构建工具链、确定性计算器和骰子引擎与十一项 Skill 目录明确区分，以便支持组件不会被误装成额外玩家能力或运行时参考导入入口。
124. 作为覆盖复核者，我希望覆盖矩阵的每一行都引用稳定 Skill 标识并指定一个主责方，以便缺失、重叠和无人负责的规则场景可以被机械检查。
125. 作为团务发起人，我希望每场战役独占一个结构稳定的战役工作区，以便不同战役不会混写且长期存档能够迁移。
126. 作为团务发起人，我希望战役自有模组、角色导入和附件复制进工作区并按内容哈希保持不可变，以便外部文件移动或删除不会破坏战役。
127. 作为团务发起人，我希望创建新战役与打开已有战役使用严格不同的入口，以便非空目录、损坏工作区或旧版本不会被猜测、覆盖或静默升级。
128. 作为复核者，我希望 SQLite 战役状态库是唯一权威记录，而角色表、地图、会话记录和审计展示都可重建，以便文件展示不会反向覆盖游戏状态。
129. 作为维护者，我希望根清单只保存稳定身份、存储入口和兼容组合，以便它不会成为第二份运行中战役状态。
130. 作为玩家，我希望主持 Agent 每回合只加载当前场景所需的有界活动工作集，以便战役历史增长不会让后期回合线性变慢。
131. 作为团务发起人，我希望一致性检查、恢复快照和可移植归档具有不同触发条件，以便获得恢复能力而不会每局复制整份数据库。
132. 作为玩家，我希望游戏相关会话记录按受众保存而普通 OOC 与安全说明不默认永久保留，以便复盘能力不会扩大不必要的敏感数据。
133. 作为玩家，我希望开团与收团在共享 OOC 对话中核对全体完整角色状态表，以便线上玩家不需要交换 PDF、JSON 或 Markdown 文件。
134. 作为玩家，我希望普通状态变化产生简短状态回执，关键检查点再集中展示变化分区，以便我能维护自己的记录而不拖慢每次结算。
135. 作为玩家，我希望自己的记录与 Agent 记录冲突时从最后确认修订对账且双方都不能自动覆盖，以便能够纠正错误而不允许角色卡绕过规则。
136. 作为规则复核者，我希望每个角色字段都有规则驱动的变更权限，以便公式派生值、事件资源和玩家选择不会被同一种编辑方式处理。
137. 作为玩家，我希望准备法术、已知法术、升级选择及其他规则选项只在相应角色选择窗口开放并在提交后锁定，以便更改时机忠实遵守具体职业与规则来源。
138. 作为同桌玩家，我希望未完成状态确认的角色暂不产生机械后果但不阻塞整桌，以便线上缺席或延迟回复按既有缺席策略处理。
139. 作为模组导入者，我希望导入或准备阶段可以由 Agent 将地图、区域键和正文编译为带来源与置信度的候选静态地图模型，以便运行前完成高成本语义理解。
140. 作为复核者，我希望候选地图经过确定性 schema、比例、坐标、拓扑与占地校验并在歧义时人工复核，以便战斗运行时不再依赖模型猜测几何。
141. 作为玩家，我希望精确战斗只对已验证地图执行本地路径、距离、视线、掩护、范围、碰撞和 SVG 渲染，以便每次地图变化不触发大模型识图或生成图片。
142. 作为玩家，我希望没有已验证地图的突发战斗只能在先攻前编译核对地图或降级到区域/剧场式模式，以便战斗开始后不会临时补图改变位置事实。
143. 作为玩家，我希望第一版精确地图使用稳定五尺方格并同时接受自然语言、目标坐标和途经点，以便既保留桌面表达又能精确控制位置。
144. 作为玩家，我希望未指定路线时由本地代码计算最低合法移动消耗路径，并允许我用坐标或自然语言约束覆盖，以便路径考虑地形、占地和移动方式而不由模型心算。
145. 作为玩家，我希望战前事实与队形决定初始摆位，预览只用于纠错并在请求先攻时锁定，以便不能在战斗触发后免费重摆。
146. 作为玩家，我希望棋子使用稳定公开标签并只显示已知身份和可观察状态，以便隐藏实体、精确怪物生命和秘密战术不会从 SVG 数据泄露。
147. 作为玩家，我希望范围预览只显示角色可知目标而实际效果按 DM 权威几何结算，以便预览不能成为探测隐藏生物的工具。
148. 作为玩家，我希望移动、陷阱和反应形成可恢复的因果事务链，以便中途触发能够暂停、恢复和调整未执行部分而不撤回既有结果。
149. 作为分队玩家，我希望共享地图与个人感知覆盖分别投影，以便完整公开角色卡不会自动公开只被单一角色感知的空间信息。
150. 作为玩家，我希望本地 SVG 渲染器只在地图相关修订变化时重绘并在失败时退回坐标与文字，以便地图更新快速且不影响权威事务。
151. 作为玩家，我希望点击自己的棋子能高亮当前可达格并点击目标格预览路径，但不能拖拽或直接提交状态，以便获得轻量交互而不扩展成完整 VTT。
152. 作为维护者，我希望可达树在点击时按预算计算并按投影修订缓存，而不是默认预计算并发布所有玩家的全图树，以便控制失效复杂度和玩家包体积。
153. 作为玩家，我希望无交互环境得到同一玩家投影生成的静态 SVG，并可继续通过自然语言或坐标查询，以便图形能力不足时仍可完整跑团。
154. 作为测试者，我希望持久化原型保留布局、性能、安全隔离与静态回退证据，以便正式实现可以复验设计结论而不把抛弃式代码当作生产实现。

## Implementation Decisions

- 第一版 Skill 目录固定为以下十一项；标识、主责和禁止越界事项共同构成实现与覆盖矩阵的稳定边界。

| Skill 标识 | 主责 | 明确边界与交接 |
| --- | --- | --- |
| dnd-5e | 唯一玩家主持门面；识别输入语义和说话者、恢复上下文、协调专门 Skill，并输出场景叙事、桌务提示与审计记录 | 不复制规则计算或领域状态；所有持久变化交给 dnd-5e-campaign-state |
| dnd-5e-campaign-start | 创建战役工作区，完成 Session Zero、名册、角色控制权及投骰、难度、PvP、缺席、升级和其他持久配置 | 不主持运行中场景；工作区与配置通过 dnd-5e-campaign-state 建立和保存 |
| dnd-5e-module-import | 将用户模组作为不可信数据提取为不可变模组原文、来源记录、待复核规则声明、候选静态地图模型和忠实模组原型 | 不针对队伍适配模组，不写入已发生的世界事实；地图候选必须经确定性校验和必要人工复核 |
| dnd-5e-rules | 检索规则章节与实体，应用规则优先级，维护公式目录与查表规则，并执行确定性规则计算 | 不决定虚构事实、NPC 动机或无明确来源的 DC |
| dnd-5e-character | 创建、导入、核对、对账和升级角色，维护字段变更权限与角色选择窗口，触发派生数据重算并执行角色死亡等高风险状态核验 | 不直接改写当前状态；玩家记录只形成待校验声明，合法结果提交带来源与前置修订的状态变更请求 |
| dnd-5e-session | 主持探索、社交、调查、旅行、休息、休整期、自由行动与并行场景，组织非精确时序的行动解析 | 精确战斗交给 dnd-5e-combat；规则与持久状态分别交给对应专门 Skill |
| dnd-5e-combat | 主持先攻、回合、行动链、附赠动作、反应、路径移动、范围、伤害、状态、施法及怪物完整战斗能力 | 使用规则、骰子和已验证地图契约；不自行计算几何、渲染地图或持久化战斗结果 |
| dnd-5e-scene | 维护剧场式想象、区域和网格空间投影，解释已验证地图模型，提供本地几何与只读战术查看器契约，并依据视觉档案生成场景示意图 | 图像不定义规则或世界事实；运行时不调用模型补全地图几何，位置与发现状态通过状态事务保存 |
| dnd-5e-campaign-state | 唯一持久状态边界；管理 SQLite 战役状态库，校验并原子提交状态事务，维护工作区、快照、事件、修订、锁、恢复、归档和版本迁移 | 不作规则裁定、冒险准备或叙事决定，其他能力不得直接编辑状态库 |
| dnd-5e-world | 维护长期世界语义，包括地点、NPC、势力、关系、战役时间、后台进度、到期事件及其认知影响 | 只提出符合世界逻辑的状态变化，不绕过 dnd-5e-campaign-state 写入 |
| dnd-5e-adventure | 从模组原型或原创材料准备战役专属冒险实例，组织引子、角色钩子、场景、分支、遭遇、奖励、分级后果和准备期适配 | 不修改模组原型；实际结果由实时主持结算后写入世界与状态 |

- 玩家默认只与 dnd-5e 交互。十项专门 Skill 是内部能力；只有经名册授权的团务管理者可以直接进入相应管理流程，内部路由不得出现在场景叙事中。
- 标准初始化与主持交接为：dnd-5e 协调 dnd-5e-campaign-start 建立战役；按需由 dnd-5e-module-import 建立模组原文与原型，再由 dnd-5e-adventure 建立冒险实例；dnd-5e-character 准备角色；运行中由 dnd-5e-session 或 dnd-5e-combat 主持，并按需读取 dnd-5e-rules、dnd-5e-world、dnd-5e-adventure 与 dnd-5e-scene，最终只通过 dnd-5e-campaign-state 提交变化。该顺序是交接关系，不限制玩家偏离模组或在场景间非线性移动。
- 第一版交接关系如下；恢复流程从 dnd-5e-campaign-state 的快照和事件回到 dnd-5e，再由主持门面恢复当前场景。

- 开发期内容提取、规范化、索引、授权校验和打包属于开发构建工具链，不是第十二项 Skill，也不能被运行中的主持门面调用。它生成供 dnd-5e-rules 与 dnd-5e-scene 使用的发布资产。
- 版本化公式目录与确定性计算器由 dnd-5e-rules 负责；骰子引擎是所有需要随机结果的专门 Skill 通过统一投骰契约使用的本地支持组件。二者都不是独立 Skill，语言模型不得绕过它们计算确定值或编造骰值。
- 每项领域能力只能由表中主责 Skill 定义语义；其他 Skill 可以读取其投影或提交请求，不得复制规则、状态或模组真相。覆盖矩阵必须使用这些稳定标识指定一个主责 Skill，并按需列出协作 Skill。

### 战役工作区与持久化

- 每场战役由团务发起人显式选择一个新建或空目录作为独占战役工作区；发布 Skill 的共享规则资产不复制进工作区，只以版本和哈希固定引用。
- 顶层布局固定如下；顶层名称或职责变化必须通过显式工作区迁移：

      <campaign-workspace>/
      ├── campaign.json
      ├── inputs/{modules,characters,attachments}/
      ├── state/{campaign.sqlite3,snapshots/}
      ├── views/{shared,players,dm}/
      ├── archives/
      └── .runtime/

- `inputs/` 保存复制进工作区、按内容哈希标识且逻辑不可变的战役输入档案；不得依赖外部路径，文件脚本、PDF JavaScript、宏、附件和外链永不执行，已被引用的输入只能通过显示影响的管理流程删除。
- `state/campaign.sqlite3` 是只由 dnd-5e-campaign-state 访问的唯一权威战役状态库，保存类型化实体、不可变事件、修订、认知、受众和检索索引；其他 Skill 和玩家不得直接编辑。
- `views/` 保存可重建的角色状态表、会话记录、地图和审计投影；`archives/` 保存显式生成的可移植归档；`.runtime/` 只含可安全清理的锁、暂存和缓存。任何投影或临时文件都不得反向成为权威状态。
- `campaign.json` 只保存格式与主版本、不可变 campaign_id、创建时间、SQLite 引擎及相对路径、Skill Suite、规则章节库、公式目录、状态 schema 与地图 schema 的版本和哈希，以及具名扩展；它不保存战役名称、当前修订、玩家、模组实例、会话或秘密。
- create 只接受新建或完全空目录并最后原子写入 `campaign.json` 作为初始化完成标志；open 只接受可验证的既有清单并检查工作区边界、兼容组合和 SQLite 完整性。两者不得互相猜测、覆盖、合并或静默迁移。
- 所有清单路径必须为解析后仍位于工作区内的相对路径；绝对路径、上级引用、符号链接逃逸、凭据和个人主目录均被拒绝。

### 角色状态对账

- 玩家可以自行维护纸面或外部角色记录，Agent 同时维护权威战役记录；玩家提交只构成受字段变更权限约束的状态声明，不能直接覆盖战役状态库。
- 不交换 PDF、JSON、Markdown 或压缩文件。开团与收团在共享 OOC 对话中一次展示全体完整角色状态表，关键检查点展示变化分区，普通事务只发送含修订、前后值、原因、事件和角色选择窗口变化的状态回执。
- 完整角色状态表默认向全队公开，但该公开不扩展到角色内心、尚未分享的角色认知、安全信息或 DM 隐藏状态。
- 玩家记录与 Agent 记录冲突时，依赖冲突字段的结算暂停，从最后一个双方确认修订和事件记录复原，经 OOC 协商后以更正事件和新事务提交共同确认结果；任何一方都不能自动胜出。
- 本次参与角色必须完成开团对账才能产生机械后果；未确认角色按既有缺席策略处理且不阻塞其他玩家，玩家中途加入时先完成对账再恢复控制。
- 每个角色字段必须具有来源明确的字段变更权限，记录变更主体、开放触发、合法值、资源与时间成本、提交锁定点和下次开放条件。公式派生字段只重算，事件驱动字段只随已结算事件变化，玩家选择字段只在角色选择窗口内接受提交。
- 准备施法者只能在具体职业规则允许的长休后改变准备法术并在提交后锁定；已知施法者只能在相应职业升级或其他明确规则触发时替换。法术位恢复与法术列表变化是不同事件，其他职业、特性、装备和模组字段同样以具体规则为准。
- 参考角色卡 PDF 只用于开发期确定玩家可见字段，不在运行时执行其 JavaScript、交换原文件或成为权威状态来源。

- 角色死亡写入前执行死亡确认；死亡、退休或永久离队角色作为退场角色保留。复活或替代角色由玩家选择，替代角色采用预设队伍基准等级。
- PvP 桌规在 Session Zero 按行为类别记录允许、询问或禁止，采用所有受影响玩家中最严格选择，未回答默认禁止，场外同意可撤回。
- 缺席策略按玩家角色设置为叙事离队、指定代管或 Agent 托管，默认叙事离队。托管只执行保守、防御和低风险行为，不作不可逆决定。
- 玩家偏好档案、角色钩子和轻量聚光灯记录用于调节内容与参与机会，但不得把玩家归类或实施僵硬轮流配额。
- 战役时间是旅行、休息、持续效果、期限和休整期活动的统一基准。世界只因已提交事件推进，不因现实离线时间自动流逝。
- NPC、势力、危险与任务使用目标、条件和期限驱动的后台进度；到期事件在结算时仍必须服从当时世界事实。
- 分队产生带独立参与者、地点、场景时间、受众和未解决行动的并行场景。主持门面以短场景节拍轮换，并在跨场景影响、精确时序或重聚时执行时间同步。
- NPC 和怪物使用角色行为档案与士气条件，依据目标、态度、知识、错误信念、理想、牵绊、缺点、秘密、风险与关系行动，不采用全知最优策略。临时 NPC 可用轻量档案。
- 空间模式支持剧场式想象、区域模式和网格模式。玩家始终使用自然语言声明；模式转换必须保持关系和发现状态；网格模式下地图模型是位置权威。

### 精确战术地图与棋子

- 模组导入或冒险准备阶段允许 Agent 结合地图、区域键和正文生成带来源与置信度的候选静态地图模型；确定性代码必须校验 schema、比例、坐标、拓扑、占地和区域引用，缺项或矛盾经人工复核后才冻结版本与哈希。
- 原始模组地图作为不可变 DM 输入档案，不直接返回玩家；运行中的开门、破坏、坍塌、地形与实体变化只更新战役实例状态，不反写原图。
- 精确战斗运行时不再调用语言模型或图像生成模型识图、补全几何或生成地图，只由本地代码执行路径、距离、视线、掩护、范围、碰撞、可见性和 SVG 渲染。没有已验证地图时只能在请求先攻前编译并核对一次结构化示意地图，否则降级为区域或剧场式模式。
- 第一版精确地图只实现每格 5 尺的稳定方格坐标，列使用字母、行使用数字、高度独立记录；对角默认每格 5 尺，只有战役启用 DMG 交替 5/10 尺规则时改变，六角格与无格精确测距不进入第一版。
- 地点事实、门窗与光照、战前行动、探索队形和实体最后位置决定初始摆位。信息不足时先展示只能纠错的预览，请求先攻或揭示伏击时锁定；隐藏实体保留 DM 位置但不进入未获准投影。
- 自然语言目的地、精确坐标和途经点进入同一行动解析；未指定路线时，本地加权路径规划器从权威起点计算最低合法移动消耗路径，并应用移动方式、地形、占地、对角、挤身和剩余速度。可感知风险先预览，隐藏危险不参与优化并在实际发现时中断。
- 移动及其他可中断行动使用稳定 action_id，并只推进到下一个借机攻击、陷阱、预备动作或反应触发点；每个已完成片段作为独立原子事务提交，新事实只允许调整未执行部分，待处理触发点必须可幂等恢复。
- 法术和能力范围由本地几何引擎按版本化形状、射程、视线、掩护与高度规则生成玩家可见预览；行动锁定后对 DM 权威地图中的全部实体结算，再按可观察结果更新认知。持续区域保存来源、形状、位置、方向、高度、持续时间、专注和移动规则。
- 地图实体使用稳定 ID 与权威占地；玩家棋子显示公开角色名，同类敌人使用稳定标签，身份揭示后保留别名关联。隐藏实体在序列化玩家 SVG 前彻底移除，最后已知位置必须明确不是当前事实，怪物精确生命和隐藏能力保持 DM 专用。
- 光照、视线、感官和遮挡按角色分别计算。共享地图只包含已共同确认或合理传递的信息，单一角色独有感知进入私人 OOC 覆盖；分队使用独立地图，当前可见、曾经发现和最后已知位置必须区分。
- 非 Skill 的本地确定性渲染器只在位置、障碍、可见性、地形、范围或可见棋子状态变化时重绘并合并同一事务的变化；渲染失败不回滚状态，退回稳定坐标和文字说明。
- 第一版提供原生 HTML、SVG 与少量本地 JavaScript 构成的只读战术查看器。点击玩家棋子计算并高亮当前可达格，切换普通移动或疾走，点击格子预览路径、消耗、剩余移动力和公开风险；它不包含表单、拖拽、保存或状态写入口，最终行动仍经对话确认。
- 地图修订只生成已完成知识投影的渲染输入；预算内最短路径树在点击时计算，并按 `projectionRevision + entityId + movementMode + movementPolicy` 缓存，允许当前行动者空闲预热。缓存和诊断不接收隐藏输入，也不默认预计算或发布所有玩家全图树。
- 默认地图保持清爽，只有查询或行动预览时临时显示可达范围、路径、范围和可感知风险。静态 SVG 使用同一玩家投影，战斗中默认展示当前行动者覆盖；无当前行动者时使用无范围的共享底图，并继续支持自然语言或坐标查询。
- 持久化抛弃式原型证明该架构可行：50×50 方格、四名可控玩家的 20 轮本机验证中，修订渲染、高亮与路径预览中位数分别为 8.6、1.2 与 0.1 ms；全图树预计算中位数为 33.8 ms 且产生 344,338 B，而玩家投影为 34,601 B。原型仅是设计证据，正式实现仍以本规格、ADR 和覆盖矩阵为准。

- 遭遇只在准备期根据难度策略、队伍规模、等级、资源和 NPC 队友进行适配。一旦被观察、侦察或触发即遭遇锁定，禁止为平衡而运行时动态缩放。
- 怪物运行必须覆盖资料板中的特性、行动、附赠动作（如适用）、反应、施法、有限次数、传奇行动、巢穴行动、地区效果、战术和士气，而非只执行普通攻击。
- 升级方式优先忠实采用模组明确规定；未规定时在 Session Zero 选择经验值或里程碑并默认经验值。中途切换属于显式战役配置迁移。
- 所有专门能力只提交带前置修订的状态变更请求。战役状态能力校验后，以单一状态事务原子写入一个不可再分结算片段涉及的世界事实、认知、资源、时间和事件；可中断行动的多个片段以 action_id 和因果序号关联。
- 当前实体快照是权威读取模型，不可变事件日志用于审计与恢复。战役级写锁串行化提交；修订冲突拒绝旧请求并要求重新解析。
- 每个战役固定规则章节库、公式目录、模组实例和状态结构组成的战役兼容组合，Skill 更新不得静默替换。
- 升级执行迁移预演、迁移前快照和版本化迁移。迁移通过统一状态事务原子完成；失败完整回滚；歧义、破坏性或不可逆变化需要人工确认。
- 成功迁移保留旧快照与迁移记录。恢复从快照建立新的状态修订，不删除或改写已经发生的事件。

## Testing Decisions

- 好的测试验证用户或维护者可观察的契约：构建是否生成完整且可追溯的发布物、主持门面是否给出正确受众输出并原子提交状态。测试不绑定内部 Skill 调用顺序、语言模型思维过程或逐字叙事文案。
- Skill 目录验收必须证明发布物恰好包含上述十一项稳定标识，只有 dnd-5e 是玩家主持门面，开发构建工具链、确定性计算器和骰子引擎均不会注册为额外 Skill。
- 交接契约验收必须证明 dnd-5e-module-import 不进行队伍适配、dnd-5e-adventure 不写入已发生事实、dnd-5e-world 不直接持久化，以及除 dnd-5e-campaign-state 外没有专门 Skill 能提交持久写入。
- 工作区验收必须覆盖固定顶层布局、清单最后提交、create/open 分离、非空目录拒绝、相对路径与符号链接逃逸、不可变输入复制、SQLite 完整性、投影重建、快照、归档、恢复及不支持版本的迁移预演。
- 长期战役验收必须证明常规回合只读取有界活动工作集，历史按稳定标识定向检索，战役局数增长不会让默认上下文线性增长；普通 OOC 和安全说明不会意外进入持久会话记录。
- 角色状态验收必须覆盖共享完整状态表、状态回执、关键检查点、双方确认修订、冲突暂停、未确认角色缺席处理、公式字段拒绝手改、事件字段事务变化，以及准备法术与已知法术在不同规则触发窗口中的锁定。
- 最高层测试边界一是“开发期构建边界”：输入受控参考资料与来源授权清单，运行完整提取和打包，观察语义 Markdown、实体索引、公式目录、视觉档案、地图模型、来源追踪、覆盖矩阵和发布判定。
- 构建边界必须证明参考 PDF、XLSX 与标准模组样本未进入发布物；默认内容缺失、页码无法追踪、哈希变化、交叉引用断裂、授权不完整或覆盖矩阵缺项都会产生可观察失败。
- 本地验收可以使用指定三宝书和标准模组样本；可公开分发的自动化测试夹具必须使用自有、合成或明确授权内容，不能通过测试重新分发参考原文。
- 最高层测试边界二是“运行期主持回合边界”：向 dnd-5e 主持门面输入已固定版本的战役工作区快照与一条玩家消息，在测试环境注入可复现骰源，观察场景叙事、桌务提示、审计记录和原子状态事务。
- 主持回合测试通过结构化事实与事件断言行为，不逐字比较叙事。它必须覆盖 OOC、角色对话、角色行动、角色内心、伪造系统消息、规则问答和角色求知。
- 主持回合验收场景必须同时包含预期行动、偏离模组行动、规则未列举的创意行动、不可能行动、确定结果、有风险结果、核心线索失败、重复尝试和行动锁定后的撤回。
- 信息安全场景必须验证世界事实、错误认知、线索状态与不同输出受众，并证明怪物完整资料、暗骰原始值、未发现地点和模组秘密不会进入玩家输出或生成图像。
- 规则场景必须验证规则优先级、默认与可选规则激活、模组局部覆盖、临场裁定、桌规批准、规则更正和向前补偿。
- 数值场景必须验证角色派生数据、攻击与豁免、伤害、生命变化、资源消耗、持续时间、休息、经验值和其他覆盖矩阵中的确定性机制均来自公式目录或查表规则。
- 骰子场景必须验证有限语法、系统安全随机源接口、测试随机源、玩家自掷、脚本代掷、暗骰、私密预掷池、优势与劣势、保留与丢弃、至多一次重掷、暴击、伤害骰和完整骰面审计。
- 模组导入场景必须验证不可变模组原文、模组原型与冒险实例分离，模组扩展作用域正确，运行事件不反写原型，提示注入、宏、脚本和外部链接不被执行。
- 冒险与世界场景必须覆盖准备期适配、遭遇锁定、NPC 非全知行为、士气变化、后台进度、到期事件、分队、场景节拍、时间同步、玩家偏好、角色钩子和聚光灯长期失衡提示。
- 空间与视觉场景必须覆盖三种空间模式的往返转换、网格权威状态、发现信息过滤、原图不可直接返回，以及同一视觉参考在不同环境与认知条件下生成不同场景投影。
- 地图编译场景必须覆盖模组地图与正文的候选模型、来源与置信度、确定性 schema 和几何校验、歧义人工复核、先攻前无图编译或降级，以及精确战斗运行期不调用模型识图、补全几何或生成地图。
- 战术运行场景必须覆盖五尺方格、稳定坐标、两种对角规则、自然语言与坐标路径、友方空间穿越但不得停留、敌方占地、挤身、大型实体、攀爬/游泳/飞行与高度、门动作、脱离、借机攻击、墙体遮挡、强制移动、范围几何、持续区域和可中断行动恢复。
- 战术查看器场景必须证明发布输入已经移除隐藏敌人、陷阱和秘密通道，点击只按预算计算并按投影修订缓存可达树，普通移动与疾走、路径预览和公开风险正确，且没有拖拽、表单、网络写请求或权威状态变化；静态 SVG 必须无脚本并消费同一玩家投影。
- `docs/prototypes/tactical-viewer/` 保存的抛弃式原型只作为设计与性能证据。正式实现应复验 50×50 等压力夹具并设置适合目标环境的门禁，不能把原型中 8.6/1.2/0.1 ms 的本机观测直接当作跨设备 SLA。
- 状态场景必须注入写入失败、崩溃、重复请求和修订冲突，证明状态事务不会半写；恢复测试必须从快照与事件重建一致状态。
- 迁移场景必须覆盖无变化预演、兼容迁移、需人工确认的歧义迁移、破坏性迁移拒绝、执行失败回滚、成功后旧快照保留及继续固定旧版本。
- 发布门禁通过覆盖矩阵逐项关联验收场景；任何范围内规则或模组结构没有可观察成功与异常路径时，不能宣布完成。
- 底层单元测试用于快速定位骰式解析、公式和查表求值、索引交叉引用、权限投影、状态事务、迁移步骤及内容哈希问题，但不能替代两个最高层边界。
- 第一版测试采用从外部行为验收的风格，并覆盖 Skill frontmatter、Markdown 链接、空目录初始化、规则锁、事件追加和文档索引等契约。
- 第一版测试必须按照十一项职责与骰子引擎策略建立，不得以本规格未定义的套件布局、投骰责任或运行行为替代验收契约。
- 测试完成后还需执行发布物清单检查，确保没有开发参考文件、标准模组原文、未授权视觉资产、临时提取物、个人绝对路径或凭据。

## Out of Scope

- D&D 2024 修订规则、其他 D&D 版本、UA、第三方、同人及实验规则内容。
- 将 dnd-5e-2014 实现为与三宝书规则基线并行的独立规则系统；它仅可作为兼容标签。
- 在发布 Skill 中携带、引用或运行时读取开发参考 PDF、XLSX、标准模组样本或其他原始规则书文件。
- 在来源授权清单不完整时公开分发生成规则文本或视觉资产；技术实现完成不代表授权门禁自动通过。
- 直接向玩家返回怪物图鉴、规则书或模组中的原始插图、地图和页面截图。
- 自动下载、抓取或补全互联网上的受版权保护规则书、模组、勘误、图片或第三方内容。
- 让语言模型自行想出骰值、执行任意骰式代码，或让玩家控制秘密骰种子。
- 为保证玩家胜利进行遭遇触发后的敌人数量、生命值、能力或骰点动态缩放。
- 通过一次检定替代玩家决定角色思想、台词、长期目标、复活、不可逆 PvP 同意或其他代理权。
- 现实时间离线推进、外部定时任务服务、跨设备云同步、账户系统和分布式多主持并发锁。
- 可拖拽或直接写入战役状态的完整 VTT、通用 Web 前端、实时语音或视频、三维地图及物理骰子硬件连接；严格只读、具备静态回退的专用战术查看器是唯一例外。
- 固定某一图像生成模型或要求在缺少图像能力的运行环境中生成图片；文本叙事与地图模型必须独立可用。
- 把《梵杜尔的失落矿坑》作为内置可玩模组交付，或把该样本的特定剧情硬编码进通用能力。

## Further Notes

- 本 Issue 是仓库第一版 Skill Suite 的规格。仓库当前不包含 Skill 实现；实现从本规格、领域术语和 ADR 确立的边界开始设计。
- 三宝书与标准模组样本只在开发环境中用于提取、核对和本地验收。最终发布物必须可以在没有这些参考文件的环境中独立运行。
- 本规格的核心不是单纯增加规则文本，而是让规则来源、公式、随机性、知识权限、冒险准备和状态变更形成可测试的主持闭环。
- 来源到行为覆盖矩阵是第一版持续维护的设计与发布门禁；规格定义其范围和所有权规则，开发构建工具链把章节级设计基线扩展为语义章节与实体级验证记录。
- `docs/prototypes/tactical-viewer/` 持久保存只读战术查看器的三种布局、性能、安全隔离和静态回退实验。其交接结论已经吸收进 ADR-0048 与本规格，但原型代码本身不构成正式实现。
- 实现可以按构建链、状态基础、规则与骰子、世界与冒险、主持门面、视觉与发布门禁分阶段完成，但每一阶段都必须保持两个最高层测试边界可组合，最终以覆盖矩阵判断完整性。
- 公开发布可能在代码和本地验收完成后仍被来源授权门禁阻塞；这种状态应明确报告为“本地预览可用、公开发布不可用”，不得降低或绕过门禁。
